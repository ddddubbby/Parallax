# RENDER_DEPLOYMENT.md - First Deploy Contract

Parallax deploys to Render from the repository-root `render.yaml`.

The Blueprint defines:

- `parallax-web`: Node web service for the Next.js app.
- `parallax-worker`: Node background worker for the polling loop.
- `parallax-db`: Render Postgres with external IP access disabled.
- `parallax-shared`: shared non-provider environment settings and generated app secrets.

## Secret model

Render stores only app-level secrets:

- `APP_PASSWORD`, prompted during Blueprint creation.
- `SESSION_SECRET`, generated by Render.
- `CREDENTIALS_ENCRYPTION_KEY`, generated by Render and shared by web and worker.

LLM provider API keys are not Render environment variables. After deployment, log in to the app and enter provider keys in Settings. The server encrypts them into `provider_credentials`.

## M0 deploy prerequisites

The Blueprint cannot successfully deploy until M0 adds:

- `package.json` with `build`, `start`, `worker`, `lint`, `typecheck`, `test`, and `db:migrate` scripts, and a `packageManager` pin matching the Blueprint's pnpm version.
- `pnpm-lock.yaml` and a `.node-version` file.
- `next.config.*` with standalone output.
- `/health` route returning HTTP 200 without database or provider calls.
- Drizzle config whose migration output path is `src/db/migrations`.
- First migration including `provider_credentials`.
- Worker entrypoint used by `pnpm worker`.
- CI that runs lint, typecheck, and tests before Render deploy.

## First deploy flow

1. Connect the repo to Render as a Blueprint.
2. Render prompts for `APP_PASSWORD`; do not add LLM provider keys in Render.
3. Render creates the web service, worker, Postgres database, generated secrets, and database references.
4. Confirm `/health` passes.
5. Log in with `APP_PASSWORD`.
6. Open Settings and add the DeepSeek API key.
7. Run mock validation before any live DeepSeek validation.

## Operational notes

- **Never delete or recreate the `parallax-shared` env group.** `CREDENTIALS_ENCRYPTION_KEY` is generated once; a regenerated key orphans every stored provider credential (D-021). Recovery from KEK loss is re-entering keys in Settings.
- **Migrations are additive-first.** The web service migrates in `preDeployCommand` while the worker may still run older code; destructive schema changes ship in a later deploy (D-024).
- **Auto-deploy vs CI:** a Blueprint deploys on push regardless of GitHub Actions unless Render's wait-for-CI option is enabled. Verify and enable that setting at first deploy; otherwise CI is advisory, not a gate.
- **Version pins move together:** the pnpm version pinned in `buildCommand` must match `package.json`'s `packageManager`; pin Node with a `.node-version` file (M0 prerequisite) so local, CI, and Render agree.
- **Standalone start:** with `output: "standalone"`, `pnpm start` must run `node .next/standalone/server.js`, not `next start`.
- **Production DB inspection:** `ipAllowList: []` blocks external connections, so `pnpm db:studio` is local-dev only; inspect production through Render's psql shell, read-only per C-6.
- **Backups are not the evidence archive.** Verify the database plan's backup retention at deploy time, and rely on the post-audit evidence archive rule in `DEVELOPMENT_GUIDELINES.md` section F for durable evidence (D-024). Upgrade the database plan when storage passes roughly 60%.

## Render assumptions verified

Render Blueprint files live at repo root by default and can define web services, background workers, Postgres databases, environment groups, generated secrets, database references, and a web health check path. Render also exposes `RENDER_EXTERNAL_URL`, which this Blueprint maps to `APP_URL`.
